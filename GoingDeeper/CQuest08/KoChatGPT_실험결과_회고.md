# KoChatGPT 업그레이드 프로젝트 - 실험 결과 및 회고

---

## 프로젝트 개요

KoGPT-2 기반 KoChatGPT 소스코드를 바탕으로 RLHF 3단계(SFT, RM, PPO) 파이프라인을 실습하고,
Foundation Model을 `skt/ko-gpt-trinity-1.2B-v0.5`로 교체하는 업그레이드를 수행한 프로젝트.

- 실험 환경: Google Colab T4 GPU (14.56 GiB VRAM)
- 베이스 모델: skt/kogpt2-base-v2 (125M)
- 교체 모델: skt/ko-gpt-trinity-1.2B-v0.5 (1.2B, LoRA r=8 적용)
- 학습 데이터: KoChatGPT 데이터셋 (SFT 12,000개, RM 1,000개 학습 / 200개 검증)

## 결과 분석

### 잘된 것

**RM Reward Score의 방향성 정상 작동**

좋은 답변(5.4216) > 나쁜 답변(1.5985) > 보통 답변(0.7481) 순서로 점수가 배분되었다.
PairWiseLoss 설계가 의도대로 작동했으며, 모델이 답변 품질의 상대적 차이를 학습했음을 확인할 수 있다.
다만 보통 답변이 나쁜 답변보다 낮게 나온 점은 추가 분석이 필요하다(아래 추가 확인 항목 참조).

이유: PairWiseLoss는 chosen-rejected 쌍의 상대적 순위만 학습하므로 절대 점수의 크기보다 순위 관계가 중요하다.
좋은 답변이 나쁜 답변보다 약 3.4배 높은 점수를 받은 것은 학습이 정상적으로 수행되었음을 시사한다.

**Trinity LoRA 학습 성공 (메모리 제약 극복)**

T4 14GB VRAM에서 1.2B 파라미터 모델 학습을 LoRA(r=8)로 성공했다.
전체 파라미터의 0.35%만 학습하면서 OOM 없이 완료된 것은 의미 있는 엔지니어링 성과다.

이유: LoRA는 attention 레이어(c_attn, c_proj)에만 저랭크 행렬을 추가해 학습하므로,
Adam optimizer 상태 메모리가 전체 파라미터 대비 0.35% 수준으로 줄어든다.
모델 전체 fp32 로드(4.8GB) + LoRA optimizer 상태(무시할 수 있는 수준) + gradient로 14GB 이내 수용 가능했다.

**파이프라인 전체 완주**

환경 설정부터 정량 평가까지 10개 섹션 전체를 오류 없이 실행 완료했다.
7가지 런타임 오류를 모두 진단하고 수정하여 최종 결과를 도출했다.

### 잘못된 것

**KoGPT2 SFT 응답 품질 미달**

4개 질문 모두 `'AI` 또는 `'AI,.` 로 동일한 패턴을 반복 출력했다.
BLEU 0.0000, ROUGE-L 0.0000으로 참조 정답과 겹치는 내용이 전혀 없다.

이유: SFT 학습이 1 epoch, batch_size=8, 12,000개 데이터로 진행되었는데,
이 조합으로는 모델이 instruction 포맷을 충분히 학습하지 못했을 가능성이 높다.
또한 eos_token_id=375(줄바꿈 토큰)로 설정되어 있어 첫 줄바꿈 직전에 생성이 종료되면
응답이 `'AI` 같은 단편만 출력될 수 있다.
데이터셋의 completion 패턴을 확인하지 않고 eos_token_id를 고정한 것이 원인일 수 있다.

**Trinity SFT 응답 대부분 빈 출력**

4개 질문 중 3개가 빈 문자열, 1개만 `'43.` 이라는 극히 짧은 응답을 생성했다.

이유: max_length=256으로 제한된 상태에서 LoRA r=8, 1 epoch 학습으로는
1.2B 모델이 instruction 포맷을 충분히 학습하지 못했다.
또한 `merge_and_unload()` 후 저장된 모델을 로드할 때 토크나이저의 eos_token_id가
올바르게 연결되지 않았을 가능성도 있다.
빈 출력은 eos 토큰이 즉시 생성되거나, generate 조건이 의도치 않게 종료 조건을 충족했을 때 나타난다.

**BLEU/ROUGE 모두 0 수렴**

세 모델 모두 유의미한 정량 점수를 기록하지 못했다.

이유: 생성된 응답 자체가 너무 짧거나(1-3 토큰) 빈 문자열이라 참조 정답과 n-gram 겹침이 발생할 수 없다.
이는 평가 메트릭의 문제가 아니라 모델 출력 품질의 문제다.
BLEU/ROUGE는 의미 있는 텍스트가 생성되어야 작동하는 메트릭이므로,
현재 결과는 생성 자체가 실패했음을 수치로 확인한 것이다.

**RM Reward Score 역전 현상**

나쁜 답변(1.5985)이 보통 답변(0.7481)보다 높은 점수를 받았다.

이유: RM 학습 데이터(1,000개)가 충분하지 않고 1 epoch만 학습했다.
PairWiseLoss는 좋은/나쁜 쌍의 상대 순위를 학습하는데,
1,000개 샘플로는 절대적 품질 기준을 확립하기 어렵다.
또한 테스트에 사용한 "보통 답변"과 "나쁜 답변"의 스타일이
학습 데이터의 분포와 다를 경우 역전이 발생할 수 있다.

**Loss 곡선 시각화 한글 폰트 미적용**

NanumGothic 폰트가 설치되었음에도 matplotlib이 이를 인식하지 못해
그래프 레이블이 깨진 상태로 저장되었다.

이유: Colab에서 `apt-get install fonts-nanum` 후 matplotlib 폰트 캐시를 갱신하는
`fm._load_fontmanager(try_read_cache=False)` 호출이 런타임 내에서 완전히 반영되지 않았다.
런타임 재시작 후 폰트를 설치하면 해결되지만, 학습 완료 후 재시작은 모델 결과를 잃을 수 있어
실질적으로 적용하기 어려운 구조였다.

## 추가로 확인해야 하는 것

**SFT 응답 패턴 원인 규명**

KoChatGPT 데이터셋의 completion 필드가 실제로 어떤 패턴으로 시작하는지 확인 필요.
`'AI`로 시작하는 completion이 데이터셋에 다수 포함되어 있다면,
모델이 이를 과적합한 것으로 볼 수 있다.
데이터 EDA를 먼저 수행한 후 SFT를 진행했어야 했다.

**eos_token_id 설정 적절성 검토**

현재 `eos_token_id=375`(줄바꿈 토큰)로 설정했는데,
이 설정이 KoGPT-2와 Trinity 양 모델에서 동일하게 적절한지 검증 필요.
토크나이저별로 줄바꿈 토큰 ID가 다를 수 있고,
Trinity는 vocab size가 51,200으로 KoGPT-2(51,200 동일)와 같지만
토큰 매핑이 동일하다는 보장이 없다.

**학습 epoch 수 증가 실험**

현재 1 epoch 학습으로는 모든 모델에서 의미 있는 instruction following이 나타나지 않았다.
최소 3-5 epoch 학습 시 결과가 어떻게 달라지는지 확인이 필요하다.
단, T4 GPU 연속 사용 시간 제한(약 12시간)을 고려한 실험 설계가 필요하다.

**Trinity SFT 빈 출력 원인 분석**

`merge_and_unload()` 후 저장-로드 과정에서 모델 상태가 온전히 보존되는지 확인 필요.
특히 generation config(eos_token_id, pad_token_id 등)가 저장된 모델에 올바르게 포함되어 있는지
`model.generation_config`를 출력해 검증해야 한다.

**LoRA rank 조정 실험**

현재 r=8로 설정했는데, r=16 또는 r=32로 늘렸을 때 메모리 수용 가능 여부와
응답 품질 변화를 비교하는 실험이 의미 있다.
r=8은 매우 작은 값으로, 복잡한 instruction following 학습에는 표현력이 부족할 수 있다.

**데이터셋 EDA 선행**

kochatgpt_1_SFT.jsonl의 completion 분포, 길이 분포, 주요 패턴을 사전에 분석하고
학습에 부적합한 샘플을 필터링한 후 재학습하면 품질 개선 여지가 있다.

## 회고

### 잘한 것

7가지 런타임 오류를 각각 원인을 분석하고 수정하는 과정에서 transformers 라이브러리의 내부 동작 방식을 깊이 이해할 수 있었다. 특히 pipeline과 model.generate()의 차이, fp16 학습 시 모델 로드 방식, LoRA와 gradient checkpointing의 조합 방법은 실패 없이는 학습하기 어려운 내용이었다.

LoRA를 활용해 T4 환경에서 1.2B 모델을 학습시키는 데 성공한 것은 실질적인 성과다. 파라미터의 0.35%만 학습해도 전체 파이프라인이 동작한다는 것을 직접 확인했다.

### 개선이 필요한 것

모델 학습 전에 데이터 EDA를 먼저 수행했어야 한다. SFT 결과가 `'AI`로 수렴한 원인이 데이터 패턴인지 학습 하이퍼파라미터 문제인지를 사전에 파악하지 못한 채 학습을 진행했다.

정량 평가 메트릭(BLEU, ROUGE)은 생성 품질이 일정 수준 이상일 때 의미 있다. 생성이 거의 실패한 상태에서 0에 가까운 수치가 나오는 것은 예상 가능한 결과였다. 다음 실험에서는 생성 샘플의 길이 분포나 instruction 포맷 준수 여부 같은 보조 메트릭을 먼저 확인하는 것이 더 효율적이다.

1 epoch 학습의 한계가 명확하게 드러났다. Colab 무료 환경의 시간 제약상 epoch 수를 늘리기 어렵지만, Google Drive에 체크포인트를 저장하며 여러 세션에 걸쳐 학습하는 방식을 고려해야 한다.

### 핵심 학습 내용

RLHF 3단계(SFT-RM-PPO) 중 SFT와 RM만 완료했고 PPO는 수행하지 못했다. 그럼에도 각 단계의 역할과 한계를 실험적으로 확인했다. SFT는 instruction 포맷 학습의 시작점이고, RM은 품질을 점수화하는 도구인데, 둘 다 충분한 데이터와 epoch 없이는 의도한 성능이 나오지 않는다는 점을 직접 확인했다.

Foundation Model 교체(125M → 1.2B)가 자동으로 성능 향상을 보장하지 않는다는 것도 중요한 발견이다. 더 큰 모델은 더 많은 학습 리소스를 요구하며, 동일한 하이퍼파라미터와 epoch 수로는 오히려 더 불안정한 출력이 나올 수 있다.
